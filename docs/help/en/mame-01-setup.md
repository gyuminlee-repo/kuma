# Step 1. Run Setup

Specify which sequencing run MAME analyzes.

## 1.1 Files & Coordinates

| Input | Format | Required |
|---|---|---|
| Reference FASTA | `.fa/.fasta` | Required |
| Consensus directory | A MAME-generated consensus FASTA folder or the raw_run output target | Required |
| CDS start (1-based) | int | Required |
| CDS end | int | Required |
| Run mode | `raw_run` or `sorted_barcode` | Required |

### Run mode

- **`raw_run`**: starts from MinKNOW `fastq_pass/<barcode*|NB*>/*.fastq(.gz)`. MAME performs minimap2 (CLI) alignment, barcode demux, Phred-aware consensus calling, and verdict by itself. This is the recommended path, where FASTQ quality is preserved.
- **`sorted_barcode`**: the path that re-analyzes MAME-generated single-record consensus FASTA per barcode. Legacy FASTA-only input has no quality string, so it uses the unweighted majority outcome, and metadata in the header such as `depth`, `consensus_n_fraction`, `mixed_positions` become the basis of the verdict.

### MAME consensus header contract

A consensus FASTA header generated by MAME can carry the following metadata.

```text
>{well_name} depth={passed_reads} input_reads={raw_well_reads} aligned_reads={aligned_reads} mapq_failed={n} span_failed={n} mixed_positions={n} max_minor_allele_fraction={f} low_depth_positions={n} consensus_n_fraction={f} low_quality_bases={n} ... consensus_n_fraction_basis=covered
```

- `depth`: number of reads that actually contributed to the consensus. Used for the optional `min_read_count` LOWDEPTH gate.
- `consensus_n_fraction`, `low_depth_positions`: evidence of insufficient per-base depth or ambiguous base calls. The denominator of `consensus_n_fraction` is the positions that reached `min_depth`, and the `consensus_n_fraction_basis=covered` marker states that definition. For handling of files before v0.13.23 that lack the marker, see `mame-pipeline.md`.
- `low_quality_bases`: number of bases excluded from the vote by the FASTQ Phred gate.
- `mixed_positions`, `max_minor_allele_fraction`: used for the AMBIGUOUS verdict so that a within-well mixture such as 51/49 does not hide as a clean PASS.
- `mapq_failed`, `span_failed`: number of reads dropped by the alignment quality/coverage filters. Shown in the Verdict table and the Excel QC columns.

## Expected mutations workbook

Step 1 has a single sub-step, 1.1. The former 1.2 was merged into 1.1 (`setup.design` remains only as a legacy id for redirects), and the expected workbook is chosen in 2.1 Inputs.


| Input | Format | Required |
|---|---|---|
| Mutation list | KURO export workbook (`expected_mutations` sheet) or a `.csv`/`.tsv`/`.txt`/`.xlsx` that only lists mutations | Required |
| Custom barcode xlsx | When using combinatorial barcodes | Optional |

A user who does not use KURO can put in a one-column mutation list as is. Well positions are not written, and the row order is the plate order. The specification is in `docs/inputs/expected-mutations.md`.

An xlsx made by KURO is matched to the project automatically through the hidden `__kuma_meta__` sheet. When a workbook with the `project_id` of another project is loaded, the app looks for the same id among recent projects and asks whether to switch.
